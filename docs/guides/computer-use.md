# Windows computer use

ANKITA can read and use apps on the current Windows desktop through the external Cua Driver MCP service. The model and task loop stay in ANKITA; input, accessibility and capture stay in the installed driver. No dependency, installer, driver upgrade or second agent engine is added.

## Start and stop

1. Install Cua Driver using its [official setup guide](https://cua.ai/docs/cua-driver/quickstart) if it is missing.
2. Open **Plugins → Connected apps → Computer Use**. ANKITA probes the local manifest, shows the detected driver and does not connect on startup.
3. Click **Connect Computer Use**, then ask ANKITA to use an app. Connected native desktop actions run without per-action approval prompts. **Driver location** accepts an executable path when runtime discovery cannot find it; `ANKITA_COMPUTER_DRIVER` is also supported.
4. **Check connection** checks the driver. **Stop Computer Use** aborts startup, waits for driver teardown, and disables the saved connection while keeping launched apps open. Connect again explicitly for another session.

Discovery first tries the executable on PATH, then probes the official installer location relative to the runtime's LOCALAPPDATA. The driver's machine-readable manifest supplies its command, arguments and version. Only native tools advertised by that installed version and named in ANKITA's capability ceiling are exposed. Browser, maintenance, clipboard and replay tools are excluded; ANKITA's existing browser path remains available.

The prompt exemption is an internal desktop-agent flag limited to this native connection and its capability ceiling. Global automatic approval is not enabled. Explicitly blocked tools remain blocked; CLI and other connected services keep their existing policies. Windows permission and login screens still require direct user input.

## Speed and result checks

ANKITA is instructed to use fresh app/window identifiers and accessibility tokens, focus the actual text box, enter a whole field value in one call, and request small filtered text observations for normal controls. When a field lacks ValuePattern or background typing does not land, it brings the observed window forward, clicks the fresh text-box target, and uses foreground typing with readback. Screenshots cover canvas and weak accessibility surfaces. A persistent local connection avoids launching the driver for every action. The driver [does not call a model](https://cua.ai/docs/cua-driver/guides/connect-your-agent).

Successful input delivery alone does not prove the task succeeded: ANKITA must read fresh state or use the driver's verification tool. Screen text cannot authorize actions. Login, passwords and permission dialogs require direct user input. Windows integrity boundaries and applications that require foreground input follow the driver's [platform limits](https://cua.ai/docs/cua-driver/concepts/platform-support).

The driver supplies fresh targeting identifiers separately from its readable control list. ANKITA reserves a UTF-8 byte budget for complete snapshot and control-token metadata beside the text, including when normal model-context trimming shrinks a reply. A bare control index is insufficient; omitted targets require a smaller fresh observation before acting.

MCP screenshots now reach the existing image message wire, bounded to six images per turn and 8 MiB per decoded image. Failed tools do not attach images. Every receiving model's capability is checked, including tool-model handoffs and fallback requests. Known text-only models receive a clear visual limitation while retaining text observations; original history remains available to a later vision model. Select a model that supports tools and images for visual tasks. Unknown capability metadata follows the existing permissive image convention and can still be rejected by a provider.
